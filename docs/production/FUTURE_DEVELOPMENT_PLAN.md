## 재개 전 현재 기준

- [현재 상태](../CURRENT_STAGE.md)의 정적 훈련판은 로컬 단일 브라우저용 Phase 0B-5 slice다. 1대1 게임 서버나 데이터베이스가 없다.
- 게임 규칙의 기준은 [여섯 기획 문서](../README.md), 지도 데이터 기준은 [MAP.xlsx](../MAP.xlsx), 화면 기준은 [UI/UX 계약](../technical/UI_UX_CONTRACT.md)이다.
- 실전 구현을 재개하려면 최종 게임명·세계관·아트 등 열린 결정과, 서비스 운영·비용·개인정보 정책을 새로 검토한다. 과거 Supabase·Vercel 프로젝트와 인증 정보가 남아 있다고 가정하지 않는다.
- GitHub Pages는 정적 훈련판의 공개 접속 경로로 유지할 수 있지만, 1대1 온라인 서버를 제공하지 않는다.

## 어디서부터 시작할까

**첫 작업은 권위 서버의 한 턴 수직 통합이다.** 현재 브라우저 로컬 판정기를 네트워크 게임으로 그대로 확장하면 각 플레이어가 상대 비밀 상태를 받을 위험이 있다. 순수 규칙을 재사용하되, 서버에서 두 명령을 받아 한 번만 판정하고 각 플레이어에게 허용된 투영만 돌려주는 계약을 가장 먼저 검증한다. 시작 전에 현재 main을 복제해 신규 작업 브랜치와 검증 환경을 만들고, 서비스·예산 승인을 별도로 받는다.

### 0. 기준선 복원과 의사 결정

1. 저장소 main, 잠금 파일, 맵 Excel, 모든 기획·기술 문서를 검토한다. pnpm install --frozen-lockfile 후 lint, typecheck, unit, production build, Playwright를 새 환경에서 다시 실행한다.
2. 공개 Pages의 브라우저 동작을 확인하고, 정적 번들에 들어간 fixture를 실전 정보 모델로 오해하지 않도록 분리한다.
3. 미결정 항목과 규칙 문서 사이의 불일치를 새 결정 기록으로 해결한다. 숫자·확률·신규 명령을 임의로 만들지 않는다.
4. 서버 호스팅, DB, 비용, 인증, 로그, 데이터 보존, 배포 방식을 현재 시점의 요구로 다시 승인받는다. 과거 Vercel·Supabase 설계는 참고 자료다.

**완료 기준:** 새 담당자가 빌드·로컬 플레이를 재현하고, 실전 범위·운영자·예산·보안 경계를 문서로 확정한다.

### 1. 서버 권위 한 턴

1. 서버 소유 canonical 경기 상태, 고정 seed·난수, 턴 마감 시각과 명령 제출·잠금 계약을 만든다.
2. 한 경기의 양측 일반·배신자 명령을 서버에서 검증·해결한다. 클라이언트가 이동 가능 여부, 비용, 성공률, 승패를 최종 결정하지 못하게 한다.
3. 모든 응답을 플레이어별 allowlist projection으로 구성한다. 비공개 요원 위치, 배신자 정보, 상대 명령과 canonical 사건을 클라이언트로 보내지 않는다.
4. 같은 상태·명령·seed가 같은 결과를 내는 테스트와, 서로 다른 시점·동시 제출·기한 만료 회귀를 만든다.

**완료 기준:** 두 관전 클라이언트가 같은 서버 판정의 서로 다른 허용 뷰를 받고, 비공개 필드 노출 검사와 한 턴 회귀가 통과한다.

### 2. 1대1 세션과 영속성

1. 닉네임, 초대 링크, create/join/cancel, waiting → setup → active 상태와 재접속을 구현한다.
2. 사용자별 단일 활성 경기 claim과 invite 만료·재발급, 중복 요청의 멱등성, 동시 참여 경합을 검증한다.
3. 저장소 선택 후 스키마·migration·권한 정책을 만들고, 서버 데이터 접근과 클라이언트 조회 범위를 분리한다.
4. 명단 은닉의 비공개 선택과 중복 시설 충돌 재선택, 자동 기본 명령, 서버 기준 마감 시간을 처리한다.
5. Realtime을 쓰더라도 메시지는 상태 변경 신호에 한정하고, 서버에서 최신 플레이어 projection을 재조회한다. 연결 끊김·중복 신호에는 polling 복구를 제공한다.

**완료 기준:** 별도 브라우저 두 대의 초대·설정·재접속·시간 만료가 실제 저장 상태에서 일관되게 동작하고, 권한 우회·중복 제출 테스트가 통과한다.

### 3. 전체 경기와 정보 보안

1. 남은 v0.7 행동·경제·시설·목표·승리·동시 충돌을 서버 판정기에 옮기고 활성 기획 문서별 테스트를 작성한다.
2. 서버가 확정한 논리 격자 경로만 3D 애니메이션으로 재생한다. 렌더링 Transform에서 게임 위치를 역산하지 않는다.
3. 양 팀의 화면·이벤트 로그를 별도로 검사하고 숨은 정보가 HTML, API, 번들, 브라우저 로그, 3D cue에 노출되지 않는지 검증한다.
4. 3D가 실패할 때 재접속과 2D 논리 화면으로 계속 플레이하는 폴백을 완성한다.

**완료 기준:** 두 명이 첫 설정부터 승패까지 플레이하고, 권한별 결과·저장·재접속·동시 충돌이 검증된다.

### 4. 플레이 품질과 출시 준비

1. 실제 Galaxy Tab S9+의 모델·OS·Chrome·CSS viewport·DPR을 기록해 가로 전용 터치·S Pen·키보드·마우스와 성능을 확인한다.
2. 명령판 겹침, 시설 이름 밀도, 카드 가독성, 3D 모션·오류·빈 상태를 실기기 피드백으로 다듬는다.
3. 공개 접근, rate limit, abuse 방지, 로그 최소화, 개인정보·운영 대응, 백업·복구, 장애 시 롤백 절차를 정한다.
4. 분리된 검증 환경에서 Preview와 2인 테스트를 거친 후, 실제 출시 범위와 공개 여부를 새로 승인받는다.

**완료 기준:** 기능·보안·접근성·기기·운영 근거가 모두 남고, 공개 출시 의사 결정이 별도로 기록된다.
